## 0. 文档定位与使用规则

本文档固化链路监控 V1 已确认的需求结论及尚待确认事项，不记录讨论、推导过程或未确认的方案建议。

自本文档创建起，后续需求分析、PRD、原型和技术方案均以本文档为唯一当前需求基线。任何新增、修改或撤销的规则，须在确认后更新本文档的“变更记录”。未列入本文档的内容不得视为已确认需求。

## 1. 需求背景与目标

### 1.1 背景

当前链路按业务分别展示，例如广电一区、广电三区的指令上下行链路。多条链路存在可复用的公共节点和公共连接关系，仅在部分处理环节出现差异；按业务各画一张完整图会造成重复维护和重复展示。

### 1.2 目标

建设面向电网业务的统一业务链路拓扑监控能力：

- 将跨区、网级、省级等业务链路统一展示在一张拓扑中；
- 将文件链路与指令上下行链路统一纳入同一拓扑底座；
- 公共 Node、符合规则的公共 Edge 不重复绘制，可由多个业务 Path 复用；
- 支持按业务链路及其业务属性聚焦或切换查看；
- 展示 Node、Role、Path、当前状态及近 30 天历史状态。

本需求监控的是业务系统、服务、中间件、组件、设备及其业务信息流转关系；网络通道承载这些信息流，但不等同于业务 Path。

## 2. 模型架构

```text
统一业务链路拓扑监控
├─ 静态拓扑模型（人工编排）
│  ├─ Node：可复用的逻辑拓扑节点
│  ├─ Edge：Node 间有方向、有业务作用的信息流转关系
│  ├─ Path：一个具体业务目标的完整静态业务拓扑
│  ├─ PathNode：Path 与 Node 的关系，承载该 Path 中的 Role
│  └─ PathEdge：Path 对 Edge 的引用
├─ 运行时执行模型（自动流转）
│  └─ Span：以 span_id、parent_span_id 等运行时信息形成实际执行关系
└─ 状态模型
   ├─ Node / Edge / Path 当前状态
   └─ Node / Edge / Path 滚动 30×24 小时历史状态
```

静态拓扑模型回答“业务理论上由哪些 Node 和 Edge 构成”；运行时 Span 回答“某次业务实际如何执行”。两者职责解耦。

## 3. 术语定义

| 术语 | 已确认定义 |
| --- | --- |
| Node（节点） | 构成业务链路的逻辑拓扑节点。包括平台、应用服务、中间件及组件、设备等。 |
| Role（角色） | Node 在某一具体 Path 中承担的功能属性。 |
| Edge（边） | 两个业务 Node 之间具有明确方向和业务作用的信息流转关系。 |
| Path（业务链路） | 完成某一具体电网业务目标所涉及的完整静态业务拓扑。 |
| Span | 业务执行时产生的运行时执行对象，用于表达实际执行关系。 |
| 当前状态 | 对象在当前时刻的状态。 |
| 历史状态 | 对象在滚动 30×24 小时内的状态变化记录。 |

## 4. Node 模型

### 4.1 节点范围与语义

Node 的当前范围包括：

- 平台：如物联网平台、非结构化平台及其他业务平台；
- 应用服务：如同步服务、文件服务、接入服务；
- 中间件及组件：如数据库、Kafka、Redis；
- 设备。

Node 是可被多条 Path 复用的逻辑资源。同一 Node 可参与多个 Path，并可在不同 Path 中承担不同 Role。

### 4.2 同一 Path 内的展示规则

同一 Node 即使在同一个 Path 的业务处理中被多次经过或承担多个 Role，拓扑中也只展示一次；该 Node 在该 Path 中的全部 Role 汇总展示。

### 4.3 实例层级

实际部署中允许存在多个实例，但一期不展示实例层级。当前拓扑以逻辑 Node 为展示和建模粒度。

## 5. Role 模型

- Role 不是 Node 的固定全局属性；其关系为 `Node × Path → Role`。
- Role 属于 Path 中的 Node 关系，即由 PathNode 承载，而不是直接属于 Node。
- 同一 Node 在不同 Path 中可有不同 Role。
- 同一 Node 在同一 Path 中可有多个 Role，展示时合并汇总。

一期 Role 完全人工维护，使用受控字典并允许多选；字典需定义互斥项、必选条件和展示顺序，具体字典内容由业务方提供或确认。已发布 Role 的修改随 Path 草稿、校验、确认发布后生效。后续可以提供候选建议，不自动覆盖已发布 Role。

## 6. Edge 模型及复用规则

### 6.1 Edge 定义

Edge 是有方向的。`A → B` 与 `B → A` 是不同的 Edge。Edge 表达 Node 间存在何种业务通信关系，不是普通的无向物理连线。

### 6.2 复用判定

Edge 不因源、目标 Node 相同而自动复用。作为同一公共 Edge 被复用，至少须同时满足：

1. 源 Node 一致；
2. 目标 Node 一致；
3. 方向一致；
4. 业务作用一致；
5. 故障影响范围一致，即该 Edge 故障时，复用它的相关业务共同不可用。

若上述任一条件不一致，即使图形上均为同一对 Node 间的连线，也应建立独立业务 Edge，并通过不同 UI 表达方式加以区分。

### 6.3 复用交互

系统对符合条件的已有 Edge 给出复用建议；人工可确认复用，也可改为创建独立 Edge。最终复用结果以人工确认或修改结果为准。

### 6.4 Edge 与运行时执行

同一 Edge 可被多个 Path 复用，也允许在一次业务执行中被多次经过。拓扑对象唯一性不等于运行时执行次数。

## 7. Path 模型

### 7.1 定义与组成

Path 是完成某一具体电网业务目标的完整静态业务拓扑，由多个 Node、多个 Edge，以及 Node 在该 Path 中的 Role 组成。

### 7.2 拓扑结构

Path 不是仅按 `A → B → C` 保存的线性步骤列表。Path 支持：

- 串行关系；
- 分支；
- 汇聚；
- 反向业务交互。

Path 的上下行是业务语义；Edge 的方向是实际 Node 通信方向，二者不要求强制一致。

### 7.3 主备边界

同一业务方向下的一个具体业务目标当前只存在一个 Path，不建模主路径、备用路径、双活路径或替代路径。同一业务对象下归组的上行 Path 和下行 Path 表达不同业务方向，不属于主备双路径。不同 Path 可复用 Node 和 Edge。

### 7.4 静态拓扑不表示执行顺序

Path 的连接关系只表达业务连接与组成关系，不表达 Node 或 Edge 的执行先后、并发或等待关系。人工编排 Path 时不配置业务执行步骤或执行顺序。

### 7.5 上下行 Path 的业务对象归组

- 指令上行和指令下行分别建立 Path；相关的上、下行 Path 可归属于同一业务对象。
- 业务对象归组当前用于用户按业务查询，以及在统一拓扑中同时聚焦相关上、下行 Path。
- 当前不提供业务对象整体启用或停用。归组内的每条 Path 仍分别执行启用和停用。
- 归组同时满足统一业务对象编码、业务目标一致、业务范围一致和方向互补；系统提示候选，人工确认。名称相似或共用 Node/Edge 不作为归组依据。
- 每个业务对象的每个方向最多一条 Path，允许暂时或合法地只有一个方向。同方向存在多个具体业务目标时拆分为不同业务对象。
- 归组关系在草稿中维护，用户确认后正式发布生效，记录建立、修改、解除操作日志。内部使用，不增设发布人员审核环节。
- 一期暂不处理业务对象整体状态，不增加该层聚合计算及展示；各 Path 的状态继续按第 9.3 节规则聚合和展示。业务对象保留查询及拓扑聚焦功能。

## 8. Span 与静态拓扑关系

- Span 是运行时对象，不属于静态人工拓扑编排对象。
- Span 在流转时携带上级 Span 标识；系统据此自行形成父子关系、实际执行顺序、分支及并发关系。
- 不需要人工维护 Span DAG，不需要人工配置 Span 执行顺序。
- Span 不要求与 Edge 强关联或一一对应；不以“Span 必须引用 Edge”作为模型约束。
- 静态 Path 用于描述理论业务拓扑，Span 用于描述实际业务运行过程。静态拓扑存在分支不代表运行时必然并发；运行时执行顺序以 Span 的上下级关系为准。
- 若后续需要将某次 Span 执行过程呈现在拓扑上，可基于 Span 自身携带的运行时标识进行匹配；该能力不构成 Edge 的基础约束。

## 9. 状态模型与聚合规则

### 9.1 基础状态

Node 与 Edge 的基础状态为：正常、异常、未知。无监控数据定义为未知。当前不定义“畅通”的具体判定算法或监控指标来源。

### 9.2 Path 聚合范围

Path 当前状态聚合该 Path 所包含的全部 Node 和 Edge 状态。

本条适用于已发布且启用 Path；停用后的最后状态展示及停止聚合遵循第 15.3 节，不把草稿或停用前历史值作为新的当前聚合结果。

### 9.3 Path 聚合结果

| 参与对象状态组合 | Path 状态 |
| --- | --- |
| 全部正常 | 正常 |
| 全部异常 | 异常 |
| 全部未知 | 未知 |
| 存在异常但非全部异常（可同时存在未知） | 部分异常 |
| 不存在异常，且同时存在正常与未知 | 部分未知 |

异常优先于未知。Path 的“部分异常”“部分未知”是聚合状态；Node、Edge 一期仅使用基础状态。

## 10. 近 30 天历史

- Node、Edge、Path 均保存当前状态及滚动 30×24 小时历史状态。
- 历史状态用于反映状态变化和持续时间；对象范围为 Node、Edge、Path 三层。
- 一期历史查询不恢复历史拓扑版本，历史状态按当前拓扑展示，并应明确提示“按当前拓扑展示”。

停用 Path 的区间处理遵循第 15.3 节；本章的保存要求不表示停用时仍生成新状态或延续停用前状态。

## 11. 人工编排与草稿、发布、启停规则

### 11.1 编排范围

一期拓扑来源为人工编排，后续可扩展自发现。人工编排仅维护静态 Node、Edge、Path 及 PathNode 的 Role；不维护运行时 Span 的执行关系。

### 11.2 草稿与发布

Path 区分草稿态与发布态。草稿用于编辑和校验；发布后成为当前用于监控与统一拓扑展示的配置。修改不应以编辑操作直接覆盖当前已发布拓扑，应经草稿、校验、发布生效流程。

一期禁止发布含孤立节点或断开子图的 Path，不提供说明理由后放行的例外；草稿仍可暂存。当前不存在此业务情况，后续确有需求时再扩展。连通性检查忽略 Edge 方向，分支、汇聚和反向交互本身不构成禁止条件；Edge 的业务方向仍保留。

### 11.3 启用与停用

Path 支持启用和停用。Path 的启停管理状态与其运行时监控状态分开维护和展示。

### 11.4 已发布共享资源

展示属性允许受控修改；业务语义属性通过复制对象并迁移引用修改，一期不建设完整 Node/Edge 版本体系。名称、说明、标签属于展示属性；Node 业务身份及 Edge 源、目标、方向、业务作用、故障影响范围属于语义属性。操作前提示影响范围，记录操作日志。

解除引用只在 Path 草稿中执行，只影响指定 Path；草稿可暂时不完整，不完整时禁止发布。逻辑停用后禁止新增引用，已有发布 Path 保留并标记待迁移，不自动转为运行异常或移除。仅未发布、零引用且无有效历史关联的对象允许物理删除，其余采用停用，状态历史和操作记录继续按保留策略保存。引用替换逐条编辑 Path 草稿，经校验、用户确认发布后生效；一期不提供批量迁移入口。

停用资源的再发布校验：比较该 Path 当前生效引用集合与拟发布引用集合。已有停用资源引用保持不变时允许发布其他修改，并提示待迁移；禁止新增对停用资源的引用。未保存的中间编辑操作不作为判定依据；已正式发布解除的引用，再次添加属于新增引用。首次发布不存在原生效引用豁免。以上放行仍须满足其他发布校验。

## 12. 一期范围与明确不做项

### 12.1 一期范围

- 统一拓扑中的 Node、Edge、Path 管理及人工编排；
- Node 与 Edge 的复用建议及人工调整；
- Path 内 Role 维护与汇总展示；
- 草稿、发布、启用、停用；
- 统一拓扑总览、业务链路聚焦或切换；
- 按业务对象查询，并在统一拓扑中聚焦其相关上、下行 Path；不提供业务对象整体启停；
- Node、Edge、Path 的当前状态及滚动 30×24 小时历史状态；
- Path 状态按既定规则聚合。

### 12.2 明确不做项

- 一期暂不处理业务对象整体状态，也不提供批量迁移；保留单条 Path 状态聚合及逐条引用替换；
- 不使用本次展示指标定义“畅通”的具体判定算法、正式阈值或告警联动；
- 不在一期展示 Node 实例层级；
- 不建模同一业务的主备、双活或替代 Path；
- 不在静态拓扑中人工配置执行顺序、Span DAG 或 PathStep；
- 不要求 Span 与 Edge 强关联；
- 不在一期恢复历史拓扑版本；
- 不在一期实现自动拓扑发现；
- 不在一期要求将 Span 实际执行过程精确映射或播放到静态拓扑上；
- 不将 Role 作为 Node 的固定全局属性。

## 15. 2026-09-15 补充确认规则

### 15.1 Node 身份及 Edge 字典 Q5–Q7

Node 使用稳定资源标识作为唯一依据；名称、类型、区域辅助判断。无稳定标识时人工确认，不自动合并。同名资源跨区域部署且故障、维护、状态可独立发生时分别建立 Node；只有作为同一逻辑资源统一监控时才复用。Edge 的业务作用、故障影响范围采用管理员维护的受控字典，并允许补充说明。

### 15.2 Span 与外部检测 Q17–Q19

现有业务方案具备 trace_id、span_id、parent_span_id、业务场景、方向、资源标识、起止时间及结果状态等字段。该结论来自用户说明，尚未实测。

关联优先使用已有稳定业务、Path/场景、Node 标识；不足时通过现有业务和资源属性解析。业务可能不支持侵入式追踪，允许外部探针提供检测结果，不强制改造业务埋点。外部检测结果可关联 Node/Edge 形成状态输入；只有具备真实执行及父子信息的数据才用于表达 Span 执行关系，不从静态连线补造真实执行链。未匹配或冲突明确标记并列出待处理记录，不按名称猜测，不将未匹配数据计入拓扑运行结果。一期控制为必要的标识关联和异常提示，不新增复杂映射治理或精确播放系统。

### 15.3 状态与历史 Q20–Q23

基础状态由外部监控能力提供，链路监控接收、展示并聚合 Path；具体畅通算法继续排除。按对象类型配置状态数据有效期，超过最后一次有效数据时间加有效期后转为未知，并显示最后更新时间；具体值依实际报告周期确定。

Path 停用后退出默认监控总览，不再生成新的 Path 聚合结果；详情保留停用前最后状态和时间，明确标识已停用。停用不直接改写为正常或未知，不停止其他 Path 对共享 Node/Edge 的使用。

历史采用状态变化区间，包含状态、开始时间、结束时间和数据来源，覆盖滚动 30×24 小时；查询和统计统一使用 Asia/Shanghai 时区。窗口起点前已开始、窗口内仍持续的状态须保留覆盖窗口的有效片段，不能因清理早期记录而丢失窗口内状态。停用前最后状态仅为历史参考，不向停用时段延续为有效实时结果。

### 15.4 权限 发布 初始化和验收 Q4 Q24

复用现有权限体系，不新建四类角色或重复设计数据权限。归组及 Path 修改采用草稿、校验、用户确认发布后生效，记录操作日志；内部使用无需另设发布人员审核。

现有链路优先通过模板导入后人工核对。验收覆盖公共前段复用、差异尾端、多业务 Edge、分支汇聚、上下行归组、五种 Path 状态、历史查询和逐条 Path 的共享资源引用替换。性能目标待确认现有 Path/Node/Edge 数量及预期增长后制定。

## 16. 总览拓扑层级与单位查询补充确认（2026-09-16）

1. 当前总览分网级、边缘节点两层。边缘节点包括省级及直连地市，例如广东、广州、深圳、广西；省—地市查询层级不表示数据必须经省级转发，省级边缘节点本身与地市边缘节点是可分别选择的对象。
2. 电网有一区至四区。区间由正向隔离装置、反向隔离装置、防火墙等隔开；跨区数据必须经过相应装置转发。网级与边缘节点之间的跨层连接也必须经过相应装置。
3. 下行至边缘四区：网级四区可直接下行到边缘节点四区；“直接”表示不绕经三区，不豁免网级—边缘之间的防火墙/隔离装置。
4. 下行至边缘其他分区：先由网级四区经装置到网级三区，再经跨层装置下行到所选边缘节点三区，再由该边缘节点三区经相应装置送至本节点二区或一区。不能把其他分区画成网级四区直接下发。
5. 上行：边缘消息先汇入本边缘节点三区，再经跨层装置到网级三区，最后经区间装置到网级四区。跨区和跨层路径必须保留装置及实际有向 Edge。
6. 总览查询新增“单位”：省—地市两级级联，支持复选。选中省级仅选择该省级边缘节点，不自动勾选或展示所属地市；地市须显式另选。多选时同时展示所选单位与网级之间的拓扑，网级公共对象保持唯一。
7. 总览查询删除“业务范围”。其他页面已有业务范围字段本次不调整。
8. 边缘节点数量多，总览须考虑多选单位和大规模拓扑的可读性。布局、折叠和分批呈现方式可作设计细化，但不得遗漏用户已选单位或将视觉可见子集当作状态聚合全集；正式规模与性能数字仍待实施确认。
9. 附件仅作层级与跨区连线示意。示意图未连 Edge 的业务节点不是有效业务拓扑规则；已确认孤立节点/断开子图禁发布原则不变。本轮不修改配置/编排页面或新增其校验流程。

## 17. 当前指标与指标趋势补充确认（2026-09-17）

### 17.1 指标对象与统计口径

1. 整条 Path 时延与分段时延分别采集，不相加、不互相推算。整链时延是 Path 起点到终点的端到端探测结果；分段时延绑定该 Path 中每一条相邻业务 Node 之间的有向 Edge。
2. 正反向隔离装置和防火墙本身均为业务 Node，因此服务到装置、装置到服务分别是独立分段，不允许跨过装置合并分段。
3. 总览当前时延显示最近一次有效探测值；数据过期或中断后显示未知，不延续旧值。
4. 分段时延、丢包率按 Path 方向统计。吞吐量为最近采集周期平均速率，按 Kbps/Mbps/Gbps 自动换算，不是累计流量。防火墙连接数为当前并发连接数，不是累计建连数。
5. 正反向隔离装置在拓扑中保持一个 Node，同时保存正向、反向两组吞吐量和丢包率；详情同时展示两组并突出当前 Path 使用方向，趋势默认当前方向并可切换另一方向。
6. 防火墙 Node 展示入向吞吐量、出向吞吐量和当前总连接数，并突出当前 Path 流向；趋势按指标分别展示。
7. 普通业务服务 Node 包括消息转发服务、Kafka、数据库等中间件或组件。逻辑 Node 不按实例拆分：单 IP 直接显示，多 IP 以“主IP + N”和完整列表呈现。总览当前指标取各 IP 最近有效数据的最差值，即最大时延和最大丢包率，并标明对应 IP；详情列出各 IP；趋势默认逻辑节点聚合并可切换具体 IP。
8. 不同指标可以来自探针或设备监控，但页面不展示指标数据来源和采集时间。指标状态使用监控数据返回的正常、异常、未知；数据过期必须为未知。暂不定义正式阈值，不改变现有 Node、Edge、Path 状态聚合。指标异常在详情标识，拓扑 Node 可显示“指标异常”角标，Node 主状态仍沿用既有状态。
9. 原型指标值默认为样例值，无需额外标注；样例数值和状态不得写成正式业务阈值或告警政策。

### 17.2 总览展示与跳转

1. Node 卡片保持名称、稳定标识和主状态，不常驻全部指标；允许显示指标异常角标。
2. 点击普通业务服务、隔离装置或防火墙后，右侧详情按 Node 类型自动展示当前指标，不显示类型说明。
3. 左侧每条 Path 摘要显示当前整链时延及指标状态；聚焦单 Path 后，画布标题区突出该 Path 当前时延。多单位或多 Path 不计算合并时延。
4. 分段时延不常驻连接线标签；选择 Edge 后在右侧详情展示当前分段时延、丢包率和指标状态，并提供指标趋势入口。
5. 从 Path 摘要进入趋势默认查看整链；从 Node 或 Edge 详情进入时携带当前 Path、方向和对象。返回总览后保留单位、业务对象、Path 聚焦和画布位置。

### 17.3 链路详情“指标趋势”页签

1. 本轮在链路详情中增加可交互“指标趋势”页签，不修改编排、配置或其他页面。
