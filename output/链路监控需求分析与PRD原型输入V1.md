> 最新范围以需求基线 V1.3 为准：一期暂不处理业务对象整体状态、不提供批量迁移；保留业务查询、拓扑聚焦、单条 Path 状态聚合及逐条引用替换。

## 0. 文档定位

本文档是基于《链路监控需求基线 V1》形成的分析和设计输入，不是需求基线本身。

- “已确认”仅指需求基线已经明确的内容。
- “待确认”对应需求基线第 13 章，未确认前不得写入正式 PRD 验收口径。
- “设计建议”用于下一轮评审和原型验证，不代表业务已采纳。
- 若本文档与需求基线存在冲突，以《链路监控需求基线 V1》为准。

本次核对已纠正旧稿中的三处越界：上下行不再分析为“一条 Path 内包含两个方向”，而是比较“同一业务对象下归组的上、下行两个 Path”和“彼此独立的上、下行两个 Path”；共享 Node / Edge 治理仍为待确认；Role 一期维护来源仍为待确认。

## 1. 已确认的设计边界

| 主题 | 已确认边界 | 对后续设计的约束 |
| --- | --- | --- |
| 静态模型 | Node、Edge、Path、PathNode、PathEdge；Role 由 PathNode 承载。 | 不增设 PathStep，不把 Role 放到 Node 全局属性中。 |
| Node | 平台、应用服务、中间件及组件、设备等逻辑节点；一期不展示实例层。 | 多实例可作为后续数据来源，但当前画布只出现逻辑 Node。 |
| Edge | 有方向、有业务作用；复用至少同时满足源、目标、方向、业务作用、故障影响范围一致。 | 同一对 Node 可以存在多条业务 Edge；UI 必须可区分。 |
| Path | 完成一个具体电网业务目标的完整静态业务拓扑；支持串行、分支、汇聚、反向交互。 | Path 不是线性步骤列表，连接关系不表示先后或并发。 |
| Span | 运行时执行对象，根据 span_id、parent_span_id 等形成实际执行关系。 | 不人工编排 Span，不要求 Span 强关联 Edge。 |
| 状态 | Node / Edge 为正常、异常、未知；Path 聚合为正常、异常、未知、部分异常、部分未知。 | 配置状态、启停状态和运行状态必须分开展示。 |
| 历史 | Node、Edge、Path 保留滚动 30×24 小时状态；按当前拓扑展示。 | 历史页固定提示“按当前拓扑展示”，不恢复历史拓扑版本。 |
| 一期范围 | 人工编排、复用建议、草稿/发布、Path 启停、统一总览、当前和历史状态。 | 不做告警联动、畅通算法、多实例展开、主备/双活、自动发现和 Span 精确回放。 |

## 2. 已部分确认项 A 上下行 Path 的业务对象归组

### 2.1 已确认结论

- 指令上行和指令下行分别建立 Path；相关的上、下行 Path 可归属于同一业务对象。
- 用户可按业务对象查询，并在统一拓扑中同时聚焦该业务对象相关的上、下行 Path。
- 暂不提供业务对象整体启用或停用；归组内每条 Path 仍分别执行启用和停用。
- 业务对象归组是 Path 的查询和展示关系，不改变 Node、Edge、Path、Span 的既定模型。

### 2.2 仍待确认的归组判定条件

创建、编辑或发布带有上行、下行业务属性的 Path 时，建议在同时出现以下特征时触发归组确认：

1. 存在业务方向相反的候选 Path。
2. 两条 Path 的具体业务目标或业务类型一致。
3. 两条 Path 面向相同的业务范围，例如相同区域、对象类型或业务场景。
4. 两条 Path 在业务语义上互为配套，共同构成一项完整业务，如指令下发与执行结果上报。
5. 存在稳定信息维持二者关系，例如统一业务编码、业务场景编码或人工维护的业务对象标识。

以上条件当前是待评审的设计建议，不是已经确认的自动归组规则。

### 2.3 不应单独触发归组的条件

- 仅复用相同 Node 或 Edge。
- 仅经过相同区域、平台或服务。
- 仅名称相似或通信方向相反。
- 上、下行分别完成不同业务目标。
- 两条 Path 没有稳定对应关系，可能出现无法解释的一对多或多对多匹配。

### 2.4 建议的触发交互

- 唯一匹配：系统提示用户确认是否归组，不自动生效。
- 多个匹配：展示候选 Path 及判定依据，由用户选择或保持独立。
- 无匹配：允许 Path 独立保存，后续可人工建立归组关系。
- 业务目标、业务范围、方向或业务对象标识变化：重新校验原归组关系。

### 2.5 剩余确认点

1. 用哪些稳定字段判定“同一业务对象”，字段由哪个系统维护。
2. 上、下行是否必须一一对应，是否允许只有一个方向的业务对象。
3. 是否需要业务对象级聚合状态。若需要，必须新增独立聚合规则；不能直接套用 Path 状态规则。
4. 业务对象归组的创建、修改和解除权限，以及是否需要操作记录。

### 2.6 待确认语句

> 已确认：相关上、下行 Path 可归属于同一业务对象，业务对象当前用于按业务查询和拓扑聚焦，不提供整体启停，归组内各 Path 分别启停。待确认：具体归组判定字段、匹配关系、归组维护权限及业务对象级聚合状态。

## 3. 待确认项 B 已发布共享 Node / Edge 的变更与退出

### 3.1 需要区分的操作

- 修改：变更对象属性，但对象标识不变。
- 解除引用：只移除某一 Path 对 Node 或 Edge 的引用。
- 引用迁移：某些 Path 从旧对象切换到新对象或新版本。
- 逻辑停用：对象保留，但限制后续使用。
- 物理删除：对象及其配置记录从当前数据中删除。

上述操作语义不同，不能在界面上用一个“删除”动作代替。

### 3.2 决策选项

| 方案 | 规则概要 | 优点 | 风险与成本 |
| --- | --- | --- | --- |
| B1 全局原地修改 | 已发布 Node / Edge 修改后，所有引用 Path 立即使用新内容。 | 操作少，维护快。 | 共享对象会让多个已发布 Path 同时变化；回溯和影响控制弱。 |
| B2 复制对象并迁移引用 | 涉及业务语义的修改时创建新 Node / Edge，选择需要迁移的 Path；旧对象继续服务未迁移 Path。 | 影响边界清晰，容易理解。 | 可能产生较多近似对象，需要命名和清理规则。 |
| B3 对共享对象做版本管理 | Node / Edge 保留稳定身份，发布新版本；Path 引用明确版本或当前发布版本。 | 审计和演进能力强。 | 版本、兼容、回退和发布流程更复杂，一期成本最高。 |

### 3.3 设计建议

建议把属性分为两类后再选方案：

- 展示属性候选：名称、说明、标签等。可评审是否允许原地修改，但必须给出影响提示和变更记录。
- 业务语义属性候选：Node 的业务身份；Edge 的源 Node、目标 Node、方向、业务作用、故障影响范围。建议优先在 B2、B3 中选择，避免无感知改变所有已发布 Path。

物理删除建议仅对“未发布且零引用”的对象开放；这是风险控制建议，仍须业务确认。已引用对象更适合先解除引用或迁移，再进入逻辑停用流程。逻辑停用不应直接改变对象运行状态。

### 3.4 必须确认的规则矩阵

| 场景 | 待确认问题 |
| --- | --- |
| 已发布且单 Path 引用 | 展示属性和语义属性分别允许怎样修改；是否必须走草稿、校验、发布。 |
| 已发布且多 Path 引用 | 是否允许全局修改；是否必须选择受影响 Path；是否需要审批。 |
| 解除某一 Path 引用 | 从 Path 草稿内移除还是可从资产侧发起；完整性校验失败时能否保存、能否发布。 |
| 逻辑停用 | 是否禁止新引用；已有发布 Path 是否继续显示和监控；是否标记“待迁移”。 |
| 物理删除 | 哪些状态和引用数满足删除条件；历史状态、审计记录是否保留。 |
| 引用迁移 | 是否允许批量迁移；迁移是否随各 Path 分别发布；失败时是否原子回滚。 |

### 3.5 建议确认语句

> 待业务确认：已发布共享 Node / Edge 采用【全局原地修改 / 复制对象并迁移引用 / 共享对象版本管理】。展示属性和业务语义属性分别执行对应变更规则。解除引用仅影响指定 Path；逻辑停用、物理删除和引用迁移按确认后的条件执行，并在操作前展示影响范围。

## 4. 待确认项 C Span 映射静态拓扑所需标识

### 4.1 边界判断

parent_span_id 只能还原运行时父子关系，不能单独判断 Span 属于哪项业务、哪条 Path 或哪个 Node。后续若要把某次执行呈现在当前拓扑上，至少要解决“执行实例识别、Path 识别、Node 识别”三层映射。该映射不要求 Span 绑定 Edge。

### 4.2 可选实现路径

| 方案 | 方式 | 适用条件 | 影响 |
| --- | --- | --- | --- |
| C1 Span 直接携带稳定标识 | Span 属性直接包含业务执行实例、Path 或业务场景、Node 的稳定标识。 | 采集规范可统一改造，业务系统能提供这些标识。 | 映射准确、解释简单；需要推动埋点或采集标准。 |
| C2 通过业务属性解析 | Span 提供服务、资源、业务类型等属性，由映射规则解析到当前 Path / Node。 | 暂时不能直接写入静态对象标识，但已有稳定元数据。 | 上线更灵活；必须管理规则版本、未匹配和冲突。 |
| C3 暂不做拓扑叠加 | Span 仅用于运行时链路查询，不映射到静态拓扑。 | 当前字段不足或映射质量不可控。 | 不影响一期已确认范围；后续补齐数据契约再进入设计。 |

### 4.3 建议核验的最小字段

| 目的 | 字段类别 | 核验重点 |
| --- | --- | --- |
| 唯一识别一次执行 | trace_id 或业务 execution_id、span_id、parent_span_id | 唯一性、跨系统传递、缺失率。 |
| 定位业务 / Path | 业务场景编码、业务类型、业务单号、方向或直接 Path 标识 | 是否稳定、是否能区分同类多条 Path、是否一对一。 |
| 定位 Node | 直接 Node 标识，或应用、服务、组件、设备等资源标识 | 是否能映射逻辑 Node；多实例如何归并。 |
| 展示过程 | 开始时间、结束时间、结果状态、错误信息 | 时钟一致性、状态字典、敏感信息边界。 |

若采用 C2，设计建议保留映射规则版本、映射结果（已匹配、未匹配、冲突）和失败原因，避免同名猜测或静默误挂。具体字段名需以真实 Span 样本和现有规范为准。

### 4.4 样本验收清单

1. 至少收集一次正常串行、一次分支或并发、一次异常、一次跨系统调用的完整 Span 样本。
2. 验证父子关系能否完整还原，异步调用是否还需要 link 等补充关系。
3. 验证每个 Span 能否稳定映射到业务执行实例、Path 和逻辑 Node。
4. 统计未匹配、重复匹配和冲突比例；未达到约定质量前不进入拓扑播放或覆盖展示。
5. 明确 Span 数据保存周期与滚动 30×24 小时状态历史不是同一数据范围。

### 4.5 建议确认语句

> 待技术与业务共同确认：当前 Span 【直接携带稳定业务 / Path / Node 标识 / 通过既有业务与资源属性解析 / 暂不具备可靠映射条件】。在映射字段、质量门槛和未匹配处置确认前，不将运行时 Span 叠加能力纳入一期验收。

## 5. 待确认项 D Role 一期维护来源

### 5.1 决策选项

| 选项 | 一期行为 | 后续演进 | 主要影响 |
| --- | --- | --- | --- |
| D1 完全人工维护 | Path 编排时人工选择一个或多个 Role，发布前校验。 | 后续再增加候选建议。 | 规则清晰、可控；维护成本较高。 |
| D2 元数据给出候选，人工确认 | 系统依据业务元数据推荐 Role，人工确认后写入 PathNode。 | 可根据采纳结果优化建议。 | 需要可靠元数据和建议来源说明，但不自动覆盖。 |
| D3 自动生成初始 Role，人工修订 | 系统自动写入初始值，人员在发布前修订。 | 可逐步提高自动化。 | 错误值更容易进入草稿或发布结果，需更强的数据质量和审计机制。 |

无论选择哪项，Role 都仍由 PathNode 承载；系统建议或自动化来源不改变 `Node × Path → Role` 的既定关系。

### 5.2 必须一起确认的口径

1. 一期采用 D1、D2 还是 D3。
2. Role 是否使用受控字典；字典由谁维护。
3. 同一 Node 在同一 Path 的多 Role 是否允许自由多选，是否有互斥或必选规则。
4. 多 Role 在拓扑节点上的展示顺序、折叠数量和完整查看方式。
5. 若采用 D2 或 D3，建议来源是 Span、业务元数据还是其他配置；建议值是否显示来源和置信度。
6. 发布后 Role 修改是否随 Path 草稿、校验、发布流程生效。

### 5.3 设计建议

若当前没有已验证的元数据质量报告，建议优先评审 D1；若已有稳定、受治理的业务元数据，可评审 D2。D3 更适合作为数据质量得到验证后的后续能力，不宜仅凭字段存在即启用。

### 5.4 建议确认语句

> 待业务确认：一期 Role 采用【完全人工维护 / 系统给出候选且人工确认 / 系统生成初始值且人工修订】。Role 使用受控字典，允许同一 PathNode 配置【一个 / 多个】Role，发布后修改随 Path 草稿、校验、发布流程生效。

## 6. 下一阶段功能清单

### 6.1 基线已确认的功能

| 功能域 | 功能 |
| --- | --- |
| 拓扑管理 | Node、Edge、Path 管理和人工编排。 |
| 复用 | Node 复用；Edge 按五项条件提供复用建议，人工确认或调整。 |
| Path 内关系 | PathNode 的 Role 维护与多 Role 汇总展示。 |

| 上下行业务归组 | 按业务对象查询，并在统一拓扑中同时聚焦相关上、下行 Path；各 Path 分别启停，不提供业务对象整体启停。 |
| 状态 | Node、Edge、Path 当前状态；Path 按已确认规则聚合。 |
| 历史 | Node、Edge、Path 滚动 30×24 小时历史，按当前拓扑展示。 |

### 6.2 需要待确认项落地后才能定稿的功能

| 依赖项 | 候选功能 |
| --- | --- |
| A 剩余规则 | 归组判定字段、匹配关系、维护权限及业务对象级聚合状态。 |
| B 共享资源治理 | 影响分析、解除引用、迁移、逻辑停用、删除、对象版本。 |
| C Span 映射 | Span 样本核验、映射规则、未匹配清单；拓扑叠加不在一期。 |
| D Role 来源 | Role 字典、人工录入、候选建议、来源和置信度展示。 |

### 6.3 一期不做

- 畅通算法、监控指标来源、告警联动。
- Node 实例展开。
- 同一业务的主备、双活、替代 Path。
- 静态执行步骤、PathStep、人工 Span DAG。
- Span 与 Edge 强关联、Span 精确映射或播放。
- 历史拓扑恢复、自动拓扑发现。

## 7. PRD 页面与原型输入

以下是信息架构和交互建议。页面拆分、字段顺序和具体控件仍需通过原型评审确认。

### 7.1 统一拓扑总览

**目标**：在一张图中融合展示已发布业务 Path，公共 Node、公共 Edge 不重复绘制，并支持按业务链路和业务属性聚焦。

**建议区域**：

- 筛选区：业务对象、业务链路、链路类型、区域层级、状态、关键字。
- 画布区：融合拓扑、图例、缩放与定位。
- 对象详情区：Node、Edge 或 Path 的属性、当前状态、引用关系和进入详情入口。

**关键交互**：

1. 选择 Path 后高亮其 Node、Edge，弱化其他对象。
2. 选择 Node 后展示其参与的 Path 及在各 Path 中的 Role。
3. 选择 Edge 后展示源、目标、方向、业务作用、故障影响范围及引用 Path。
4. 同一对 Node 间存在多条业务 Edge 时，通过可区分的线型、间距、标签或展开交互展示，不能合并成一条未说明的连线。
5. 拓扑连线只表达业务连接，不在静态总览中标注执行序号。
6. 状态不能仅依赖颜色，应同时使用图标或文字。
7. 选择业务对象后，同时聚焦该对象下的上、下行 Path；业务对象详情不提供整体启用或停用操作。

### 7.2 Path 管理

**目标**：查询和管理 Path 的草稿、发布、启用、停用及进入编排的入口。

**建议字段**：Path 名称、所属业务对象、业务目标或业务标识、链路类型、上下行属性、配置状态、启停状态、当前运行状态、当前发布版本、更新时间。归组判定字段仍待确认，版本字段的含义需与 B 的方案保持一致。

**关键约束**：配置状态、启停状态和运行状态分列；编辑已发布 Path 时先产生草稿，校验并发布后才替换当前监控配置。

### 7.3 Path 编排

**目标**：人工维护 Path 的 Node、Edge、PathNode Role 和 PathEdge 引用，不维护运行时执行关系。

**建议交互**：

1. 从 Node 库选择已有 Node 或按权限创建 Node。
2. 在两个 Node 间选择已有 Edge 或创建 Edge；系统按五项复用条件给出候选，人工最终决定。
3. 对当前 Path 中的 Node 维护一个或多个 Role；录入方式依赖 D。
4. 支持串行、分支、汇聚和反向交互；不提供执行步骤号、并发配置或等待条件。
5. 同一 Node 重复加入当前 Path 时不新增第二个图形节点，转为定位已有 Node 并维护其 Role。
6. 发布前校验 Path 引用关系完整、Edge 两端 Node 已纳入当前 Path、必填 Role 已维护；共享资源影响校验依赖 B。

### 7.4 Node / Edge 资产与引用详情

**目标**：查看逻辑拓扑资产、复用情况和变更影响。

**建议内容**：基础属性、当前状态、近 30 天状态入口、引用 Path 清单。修改、解除引用、迁移、停用和删除按钮需在 B 确认后定稿；在此之前原型应以“待确认规则”标识，不展示为可直接执行的确定流程。

### 7.5 Path 监控详情与历史

**目标**：解释一条 Path 的当前聚合状态，并查看滚动 30×24 小时状态变化。

**建议内容**：Path 属性、配置状态、启停状态、运行状态、当前拓扑、异常或未知对象清单、状态时间轴、时间选择器。

**历史交互约束**：切换历史时间只改变状态数据，不恢复旧拓扑；页面持续显示“按当前拓扑展示”。状态采集频率、未知触发条件和历史记录粒度尚未在基线中定义，应作为后续技术与产品待确认参数。

## 8. 原型必须覆盖的场景

| 场景 | 必须体现的内容 | 依据状态 |
| --- | --- | --- |
| 公共前段、差异尾端 | 两条 Path 复用公共 Node / Edge，尾端使用各自 Node / Edge。 | 已确认模型的典型业务示例。 |
| Node 多 Path 多 Role | 同一 Node 在不同 Path 承担不同 Role；同一 Path 多 Role 汇总。 | 已确认。 |
| 多业务 Edge | 同一对 Node 因业务作用或故障影响范围不同而存在多条 Edge。 | 已确认。 |
| Path 拓扑结构 | 串行、分支、汇聚、反向交互。 | 已确认。 |
| 状态组合 | 正常、异常、未知、部分异常、部分未知及原因解释。 | 状态值和聚合规则已确认；解释交互为设计建议。 |
| 历史查看 | 当前拓扑叠加历史状态，并显示“按当前拓扑展示”。 | 已确认。 |
| 上下行归组 | 按业务对象查询并同时聚焦相关上、下行 Path；两条 Path 分别启停。 | 归组用途和无整体启停已确认；归组判定与业务对象级状态待确认。 |
| 共享对象变更 | 多 Path 引用下的修改、迁移、停用和删除。 | 先做流程对比，等待 B 确认。 |

## 9. 可直接写入 PRD 的已确认规则

1. 系统应以 Node、Edge、Path、PathNode 和 PathEdge 构建统一业务链路静态拓扑；Role 由 PathNode 承载。
2. 同一 Node 可被多条 Path 复用，并可在不同 Path 中承担不同 Role；同一 Path 内同一 Node 只展示一次，其多个 Role 合并展示。
3. Edge 有方向并承载业务作用。Edge 复用至少同时满足源 Node、目标 Node、方向、业务作用和故障影响范围一致；系统给出复用建议，人工可确认或调整。
4. Path 表达一个具体电网业务目标的完整静态业务拓扑，支持串行、分支、汇聚和反向交互；连接关系不表达执行顺序、并发或等待。
5. Span 为运行时对象，根据 span_id、parent_span_id 等形成实际执行关系；不人工维护 Span DAG，不要求 Span 与 Edge 强关联。
6. Node、Edge 的基础状态为正常、异常、未知；无监控数据为未知。Path 聚合其全部 Node 和 Edge，并按需求基线第 9 章的规则生成五种状态。
7. Node、Edge、Path 保存当前状态及滚动 30×24 小时历史状态。历史状态按当前拓扑展示，页面应提示“按当前拓扑展示”。
8. Path 区分草稿态和发布态；修改已发布拓扑应经草稿、校验、发布后生效。Path 启停管理状态与运行状态分开维护和展示。
9. 一期采用人工静态拓扑编排，不展示 Node 实例层级，不恢复历史拓扑，不实现自动拓扑发现、告警联动、畅通算法或 Span 精确映射播放。
10. 相关上、下行 Path 可归属于同一业务对象。系统应支持按业务对象查询，并在统一拓扑中聚焦该对象相关的上、下行 Path；暂不提供业务对象整体启停，各 Path 分别启停。

尚不得写入正式 PRD 的规则：上、下行 Path 的具体归组判定字段、匹配关系、维护权限及业务对象级聚合状态；共享 Node / Edge 的具体变更和退出规则；Span 到 Path / Node 的稳定映射字段；Role 一期由人工还是系统辅助维护。
