## 批量迁移的业务场景 仅供后续参考

当前一期不提供此批量流程，逐条编辑 Path 草稿即可完成引用替换。以下保留场景说明。

此处迁移指修改静态拓扑中的引用关系，不负责实际服务部署、流量切换或业务数据迁移。

例：广电一区指令下行、广电三区指令下行和文件分发三条 Path 共用“接入服务 A”。服务调整后，其中两条业务改用逻辑服务 B，另一条继续使用 A。

1. 新建 B，以及连接 B 所需的业务 Edge；Edge 端点变化时不能原地修改影响其他 Path。
2. 从 A 的引用清单选择需要替换的两条 Path。
3. 为各 Path 形成草稿，替换 Node/Edge 引用；检查 Role 是否仍适用并由维护人员确认。
4. 校验并分别发布。第三条 Path 保持引用 A；旧对象在仍有引用时继续保留。

适用情况还包括共享中间件替换、某组业务通信关系调整、旧逻辑资源退役前的集中替换。仅修改名称、说明、标签通常不需要迁移；同一逻辑 Node 下实例扩缩容也不触发逻辑拓扑迁移。

一期已选择逐条编辑草稿完成替换。若后续频繁调整多条 Path，可再评估批量生成草稿及逐条发布流程；本期不实现该批量入口。

## 整体状态早期建议 暂不实施

用户最新确认暂不处理业务对象整体状态。以下为历史建议，未采纳为当前算法，后续重新启用该能力时再评估：业务对象取其已发布且启用 Path 所包含的 Node/Edge，按各自标识去重后套用基线第 9.3 节规则，不直接把“部分异常”等 Path 聚合值当作基础状态再次计算。

- 一个方向停用：仅聚合仍启用方向，额外标明另一方向停用，避免用户误解为完整双向正常。
- 全部方向停用：管理状态显示“全部停用”，当前整体运行状态显示“—”，不使用旧状态充当实时结果。
- 合法单方向业务：仅聚合该方向实际对象，不因不存在另一方向而补一个未知。

这项补充是为落实整体状态所需的参与范围与停用边界，不改变单条 Path 的既定聚合公式。业务对象独立历史存储未被本轮要求，保持 Node/Edge/Path 三层历史边界。
